# 架构转折：从"AI 全权决定"到"聊天归 AI，推任务归 Python"

## 起因：一个朋友的反馈

朋友测试时说："我天天感觉困怎么都睡不够怎么办"，DS 推荐"打开窗户呼吸"。朋友说"不想动"，DS 回复变得一板一眼。

朋友的原话："你希望他回答你什么？人有时候抛出问题不是为了要解决方案，有可能就是想聊聊天扩宽一下自己的思路。感觉这个 AI 目前缺乏判断'这个人是想聊天还是需要解决问题的方案'的能力。"

## 根因分析

当时的架构：DS 每轮都要输出 JSON，包含意愿判断、状态判断、任务推荐。这意味着 DS **每一轮都在"评估模式"**——不管用户是想聊天还是想干活，DS 脑子里永远在想"我该推荐什么任务"。

这就是为什么它会对"困怎么办"推荐"打开窗户"——它在执行"给出具体可执行建议"的规则，而不是在跟朋友聊天。

## 第一次大修：v3 聊天优先 + 按需干活（2026-04-01）

- DS 自主判断输出纯文本（聊天）还是 JSON（干活）
- 聊天模式下不触发守门校验、不展示按钮
- 同时重做人设系统：从"管家"定位改为"朋友"，5种 MBTI 风格人设

**效果：** 活人感大幅提升。但 DS 还是会在聊天时惦记着"要不要切到干活模式"。

## 第二次大修：v4 聊天归 AI，推任务归 Python（2026-04-02）

核心改变：**DS 根本不需要知道"推不推任务"这件事。**

- DS 只负责自然聊天 + 输出观察信号（energy_impression、emotion、activity_category、user_attitude）
- Python 读信号，自己决定要不要触发第二次 API 调用推任务
- DS 的 prompt 里没有任何关于"推荐任务"的内容

**架构图：**
```
用户输入 → call_chat（DS 自然聊天 + 信号）
         → Python 解析信号
         → 不触发 → 纯聊天，无按钮
         → 触发   → call_task（第二次调用）→ 守门校验 → 展示按钮
```

## 为什么这个架构改变是根本性的

之前不管怎么优化 prompt，DS 永远在"评估模式"，因为它知道自己有推荐任务的职责。把这个职责从 DS 身上拿掉，DS 才能真正放松下来聊天。

**类比：** 就像一个朋友如果知道他的任务是"在合适的时候给你建议"，他聊天时就永远在找时机。但如果他的任务只是"陪你聊天"，他反而会自然地在合适的时候说出有用的话。

## 方法论

1. **如果 AI 在做一件事的时候同时想着另一件事，两件事都做不好** — 职责分离不是代码架构问题，是 AI 心理问题
2. **把判断逻辑从 AI 移到确定性代码里** — AI 负责感知（输出信号），Python 负责决策（规则引擎）
3. **朋友的一句非专业反馈可能比十次技术优化更有价值** — 用户感知是产品设计的第一手信号
