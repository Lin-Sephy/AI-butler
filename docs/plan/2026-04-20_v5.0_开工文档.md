## 一句话目标

把 v4 的"聊天+任务判断混在一次调用里"拆成双模式架构，DS 自由聊天，Python 做确定性执行，数据按需查不监控。

---

## 为什么重构（三句话版）

1. v4 的 6 字段信号块逼 DS 每轮扫描用户，聊天带监测感，角色撑不起来
2. 用户不需要 AI 推荐任务——他们打开 app 时自己知道要做什么，不信 AI 建议
3. AI 的真正价值是帮用户把发散思维结构化，这需要 DS 自由，而不是被规则约束

## 11 条核心决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 双模式：闲聊 / 计划，用户主动切 | 一次调用只做一件事，DS 不再被两个职责撕扯 |
| 2 | 身份：成了精的白鼬 | 真白鼬触发 DS 自我设限（"我不懂代码"），成精切到智慧灵兽类 |
| 3 | 闲聊模式极简 prompt，无规则无禁令无信号块 | DS 无约束时扮演质量最好，约束搬到系统端 |
| 4 | MBTI 三套人设保留，作为 custom_persona 预设 | 用户可选、可自填、可留空 |
| 5 | LLM 核心价值是帮用户结构化发散思维 | 不是推荐任务，不是监控状态 |
| 6 | 可靠性标杆：掌握时间线和进度，主动提供实用信息 | 参见 `docs/conversations/给小克看/给小克看.TXT` |
| 7 | 信息架构：可查不可监 | DS 平时不知道数据，用户提起才查。避免监测感 |
| 8 | 任务记录即写入（status=idle），7 天可查 | 记了没做的任务 DS 也能跟进 |
| 9 | 长期项目追踪：project 表 + 摘要覆盖更新 | 回答"做到哪了" |
| 10 | 日程：task 表加 event 类型 + user_profile 加 daily_routine | 不建新表，复用现有结构 |
| 11 | 精力值全砍 | "此刻"精力对规划明天无意义；状态差用户会自然说 |

## DB Schema 变更

### task 表

```sql
-- 扩展 task_type 枚举
ALTER TABLE task ADD CONSTRAINT task_type_check
  CHECK (task_type IN ('work', 'rest', 'event'));

-- 新增 project 关联
ALTER TABLE task ADD COLUMN project_id UUID REFERENCES project(project_id);
```

**event 类型规则**：
- 有 scheduled_at，无 duration
- 不进入专注流程（不能"开始专注"）
- 只出现在日程视图和计划模式数据里

### user_profile 表

```sql
ALTER TABLE user_profile ADD COLUMN daily_routine TEXT;
-- 示例值："8:30 开始学习；12:00-15:00 休息；18:00-19:00 吃饭；22:00 休息"
```

### project 表（新建）

```sql
CREATE TABLE project (
    project_id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES auth.users(id),
    name TEXT NOT NULL,
    keywords TEXT[] NOT NULL,           -- 用于自动匹配 task
    summary TEXT DEFAULT '',             -- LLM 覆盖更新
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- RLS 策略同其他表
```

### 1. 闲聊模式 prompt

```
你叫"{companion_name}"，一只成了精的白鼬，我是你的铲屎官。

{custom_persona}  ← 用户填了才有，没填就没这段
```

**砍掉**：回复原则、绝对禁止、输出格式、信号块说明。

### 2. 计划模式 prompt

```
你叫"{companion_name}"，一只成了精的白鼬，我是你的铲屎官。

{custom_persona}

你的铲屎官现在需要你帮忙梳理计划。
（具体措辞待定，见待定项）
```

**输出信号**：
- 默认不输出任何信号
- 用户明确表示"行""就这样""记下来"时，输出：

```
---judgment---
{"confirmed": true}
```

Python 看到 `confirmed: true` → 拿对话记录调专用 LLM 提取结构化 tasks → 弹确认界面 → 用户确认 → 批量写入。

### 3. EXTRACT_PROMPT

现有维度保留，新增 `project_updates`：

```json
{
  "reinforced": [...],
  "contradicted": [...],
  "new_impressions": [...],
  "daily": {...},
  "session_summary": "...",
  "project_updates": {
    "毕业论文": "导师要求第三章重写分析部分，deadline 推到下周五"
  }
}
```

提取时把**用户当前项目列表 + 各项目现有摘要**传给 LLM，让它判断对话里有没有涉及项目的新信息，有就压进去更新。

## 核心原则（写在代码注释里的哲学）

### LLM 与 Python 的分工

LLM 是概率引擎，Python 是确定性引擎。两者配合，不是二选一。

- **LLM 负责**：理解意图、识别实体、评估优先级、生成草稿、判断确认——"不确定输入 → 不确定输出"
- **Python 负责**：弹按钮、写 DB、状态流转、去重计数、关联项目——"确定输入 → 确定输出"

不是让 LLM 直接干，是给 LLM 配可靠的执行器。LLM 说"用户确认了"，Python 负责"提取 tasks → 弹界面 → 写入"。

### 可查不可监

DS 平时不知道任务/项目/日程信息。需要时才查（function calling 或 Python 静默补）。

**不要把用户的全部数据默认塞进 system message**，那样 DS 会主动提起，用户会感觉到被监控。

### 系统端守门

DS 输出完全自由，没有 prompt 规则约束它。

所有约束在系统端：Python 解析输出 → 决定弹什么按钮 / 写什么数据。DS 的输出质量不是靠"规定它怎么输出"保证的，是靠"不管它怎么输出，Python 都能正确处理"保证的。

## 风险清单

| 风险 | 严重度 | 应对 |
|---|---|---|
| DeepSeek function calling 质量差 | **高** | Step 0 必过，不过就退回方案或合并工具 |
| DS 计划模式下不输出 confirmed 信号 | 中 | 实测调整 prompt，或 Python 做兜底关键词匹配 |
| 闲聊模式 Python 关键词匹配噪音大 | 低 | 只匹配已建项目的 keywords + 已有任务 keyword，不做通用匹配 |
