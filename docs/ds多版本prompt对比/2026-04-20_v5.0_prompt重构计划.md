# v5.0 Prompt 重构计划

**日期**：2026-04-20
**相对基线**：v4.2.1（当前生产）+ v4.3 触发式信号块（未上线的候选）
**性质**：产品级重构，不是参数调优

---

## 为什么要重构

v4 系列的根本问题：**聊天和任务判断塞在同一次 LLM 调用里。**

DS 被迫同时做两件事——自然聊天 + 每轮填 6 字段信号块。结果是：
- DS 变成"用户扫描仪"，每轮都在分析用户状态，聊天带监测感
- prompt 里的"绝对禁止"让 DS 缩手缩脚，倾向于问问题来规避风险
- 反复提及任务相关内容，DS 就往推任务方向偏；不提任务，又变成纯角色扮演，放在专注产品里不伦不类

v4.3 触发式信号块试图在技术层面修补（只在触发时输出信号），但没解决底层矛盾。

### 产品层面的认知更新

1. **用户不需要 AI 推荐任务。** 他们在做计时之前就知道自己想做什么，也不太信 AI 的建议。
2. **AI 的真正价值是帮用户把发散思维结构化。** 用户是自由发散的，LLM 擅长把发散的东西变成可执行的计划。
3. **可靠性 > 可爱。** 先好用再被喜欢。可靠 = 掌握用户时间线和进度，主动提供此刻需要的信息，不废话。
4. **可靠性的标杆**：见 `docs/conversations/给小克看/给小克看.TXT`——通过时间戳判断状态、主动提供日程和路线、简短精准、持续跟踪进度。

---

## 核心决策（已确认）

### 1. 双模式架构：闲聊 / 计划，用户主动切换

不再让 DS 在一次调用里同时承担陪聊和任务判断。两个模式各自独立：

| | 闲聊模式 | 计划模式 |
|---|---|---|
| 谁触发 | 默认 / 用户切回 | 用户主动切入 |
| DS 的角色 | 陪伴，自由聊天 | 帮用户把想法变成计划 |
| 信号块 | 无（彻底没有） | 仅 `confirmed: true`（用户定了才输出） |
| 精力值 | 不采集 | 不采集（已砍，见第 11 条） |
| 数据查询 | Python 关键词匹配兜底 | DS 通过 function calling 按需查 |
| prompt 风格 | 极简，不限制 | 身份不变，插入计划模块 |

用户主动切换意味着系统不需要猜意图，DS 不需要扫描。

**prompt 结构（可插拔）**：

```
身份（固定）：你叫"{companion_name}"，一只成了精的白鼬，我是你的铲屎官。
性格（可选）：{custom_persona}  ← 用户填了才有
计划模块（可选）：{plan_module}  ← 计划模式开启时插入
```

闲聊模式 = 身份 + 性格（如有）。计划模式 = 身份 + 性格（如有）+ 计划模块。小白还是小白，不换身份。

**计划模块内容**：

```
你的铲屎官现在需要你帮忙梳理计划。
```

不写回复原则，不写输出格式限制，DS 自由输出。DS 通过 function calling 按需查询数据（任务记录、统计、项目摘要、日程），不预先塞入。具体措辞待定（见待定项 A）。

### 2. 身份定义

```
你叫小白，一只成了精的白鼬，我是你的铲屎官。
```

- "成精"解决 DS 自我设限问题（不会觉得自己只是动物不懂人类的事）
- 默认名"小白"，用户可改（companion_name 参数保留）
- 用户可选填 custom_persona（自定义性格描述），填了就追加到身份后面

### 3. 闲聊模式 prompt：极简

```
你叫"{companion_name}"，一只成了精的白鼬，我是你的铲屎官。

{custom_persona}  ← 用户填了才有（可选 MBTI 预设或自填）
```

- **无回复原则**
- **无绝对禁止**
- **无信号块**（彻底没有，包括 energy_impression 也不采集）
- **MBTI 三套人设保留**，作为 custom_persona 的预设选项；用户也可自填或留空
- DS 性格从对话中自然长出来，跨 session 靠记忆系统维持一致性

### 4. 开场白

- **首次见面**：写死一句，锚定调性（具体内容待定）
- **日常打开**：DS 根据记忆 + 当前时间自己生成（每次不同）

### 5. LLM 核心价值定位

用户自由发散，LLM 帮用户把发散思维结构化、逻辑化。这是 DS 本来就擅长的事，不需要 prompt 教它怎么做，需要的是**喂足够的信息**。

### 6. 可靠性方向

可靠 = 掌握用户的时间线和进度，主动提供实用信息。

需要的信息（现有 vs 缺失）：

| 信息 | 现状 | v5.0 方案 |
|---|---|---|
| 时间戳 | ✅ build_chat_message 已传当前时间 | 不变 |
| 聊天记录 | ✅ session summary + chat history | 不变 |
| 任务记录 | ✅ task 表 + 任务栏（只有当前） | 扩展为最近 7 天记录，**可查** |
| 记忆系统 | ✅ 每日快照 + 长期印象 | 不变 |
| 用户日程 | ❌ 只有单条 scheduled_at | task 表新增 event 类型 + user_profile 存 daily_routine，**可查** |
| 长期项目进度 | ❌ 任务一次性，无 project 层级 | 新增 project 表，**可查** |

### 7. 信息架构：可查不可监

**原则**：DS 平时不知道任务/项目/日程信息。需要时 Python 通过关键词匹配把相关数据喂给 DS。不默认塞进 system message，按需查询。

**统一触发机制**：用户聊天中提到关键词 → Python 匹配命中（任务 keyword / 项目 keywords）→ 把相关数据附在本轮 message 里。DS 不知道这些系统的存在，Python 在背后补信息。

**DS 可查的三层数据**：

| 层 | 内容 | 来源 | 用途 |
|---|---|---|---|
| 原始记录 | 每条任务的完整状态和时间 | task 表（已有） | DS 需要细节时查 |
| 统计数据 | 最常专注时段、平均时长、完成率 | Python 从 task 表实时算 | 计划模式喂 DS + 第四页前端展示，共用一个查询 |
| 项目摘要 | 项目上下文（deadline、进展、决定） | LLM 从聊天提取，覆盖更新 | 计划模式喂 DS |

### 8. 任务记录：记录即写入，7 天可查

用户点"记录"时任务就写入（status=idle），不等完成。DS 可查的任务状态：
- **记了没做的**（idle）→ DS 能跟进
- **做了没完成的**（in_progress / paused）→ DS 能知道进度
- **做完了的**（completed）→ DS 能回顾
- **放弃的**（abandoned）→ DS 也能看到

task 表已有 created_at / started_at / completed_at，数据已经在了。需要的只是一个"最近 7 天任务记录"的查询接口。

### 9. 长期项目追踪

新增 project 表：

```
project 表
├── project_id
├── user_id
├── name: "毕业论文"
├── keywords: ["论文", "第三章", "导师"]  ← 用于自动匹配
├── summary: "第三章初稿已写完，导师要求重写分析部分。deadline 下周五。"
├── created_at
├── updated_at
└── 关联的 task 记录（通过 keyword 自动匹配，用户可手动调整）
```

**项目创建**：用户主动建（"新建一个项目叫毕业论文"），这样用户知道这个功能存在。

**任务自动归属**：新任务的 keyword 匹配项目 keywords 时自动挂到项目下。用户可手动调整，防止挂错。

**项目摘要（project summary）**：
- 由 `extract_and_update` 流程自动维护——每次提取印象时，如果检测到对话涉及某个项目，把新信息合并到该项目的 summary 里
- 覆盖更新（不是逐条追加）：LLM 把旧摘要 + 新信息压成一段新摘要，自然丢掉过时信息
- 跟 session_summary 的更新逻辑一致，走同一条管道，只是多了一个按项目分拣的维度

**EXTRACT_PROMPT 改动**：在现有提取维度上新增 project_updates：

```json
{
  "reinforced": [...],
  "contradicted": [...],
  "new_impressions": [...],
  "daily": {...},
  "session_summary": "...",
  "project_updates": {
    "毕业论文": "导师要求第三章重写分析部分，deadline 推到下周五"
  }
}
```

提取时把用户当前项目列表 + 现有摘要传给 LLM，LLM 判断对话中有没有相关信息需要更新。没有就不写。

**可查机制**：用户提到项目相关词 → Python 匹配 → 拉出 project summary + 7 天关联任务 → 一起喂给 DS。

### 10. 日程结构

**一次性事件**：复用 task 表，新增 event 类型。task_type 从 `"work" | "rest"` 扩展为 `"work" | "rest" | "event"`。event 类型有 scheduled_at，没有 duration，不进入专注流程，只出现在日程视图和计划模式数据里。

**日常作息**：存在 user_profile 表，新增 daily_routine 字段。用户设置一次可随时修改。

```
daily_routine: "8:30 开始学习；12:00-15:00 休息；18:00-19:00 吃饭；22:00 休息"
```

计划模式下 DS 拿到：日常作息（用户理想）+ 今日事件 + 7 天任务记录（实际行为）+ 统计数据 + 项目摘要。DS 自己对比理想与现实。印象系统会逐步积累用户的实际行为模式（如"实际起床时间约 11 点"），进一步修正。

### 11. 精力值：砍掉

v4 的精力系统（5 档 + energy_impression 信号块 + 偏差检测）全部砍掉。

- 闲聊模式不采集
- 计划模式也不采集——用户可能在规划明天或下周，"此刻"的精力值没有意义
- 用户状态差时会在对话中自然表达（"明天可能状态不好，别排太满"），DS 直接从自然语��理解，比 1-5 档数字更准
- 印象系统 + 7 天任务记录会积累用户的实际状态趋势，DS 可查

- 数据查询通过 function calling，DS 按需调用（见 C）

**计划模式下 DS 的判断职责**：

DS 在计划模式下做两件事：
1. **自由对话**：帮用户梳理计划，多轮打磨，直到用户满意
2. **判断用户是否确认**：每轮判断用户定没定。定了才输出信号：

```
---judgment---
{"confirmed": true}
```

- 用户还在讨论/调整/犹豫 → 不输出信号，继续聊
- 用户明确表示"行""就这样""记下来" → 输出 confirmed

**DS 不负责结构化提取。** 用户确认后，Python 拿对话记录调一次专用 LLM 提取结构化 tasks（keyword / minutes / nature / project / urgency），弹确认界面给用户，用户确认后批量写入 task 表。

这样 DS 始终只做一个判断：用���定没定。结构化提取交给专用 LLM 调用（跟 extract_and_update 同一思路：LLM 做判断，Python 做执行）。

**LLM 与 Python 的分工原则**：
- LLM（概率引擎）：理解意图、识别用户确认信号、生成计划草案、评估优先级
- Python（确定性引擎）：弹按钮、写 task 表、状态管理、关联项目、去重

**待定**：
- 计划模块的具体措辞（怎么告诉 DS "现在帮忙梳理计划"）

### C. ~~系统端守门规则~~ → 已确认，见下

**数据查询机制：DS function calling + 闲聊兜底**

- **计划模式**：通过 DeepSeek function calling，DS 按需调用查询工具。工具定义只在计划模式注册，闲聊模式不注册。

```
可用工具：
- query_tasks(days)    → 最近 N 天任务记录明细
- query_stats()        → 专注统计（时段、时长、完成率）
- query_project(name)  → 项目摘要 + 关联任务
- query_schedule()     → 今日事件 + 日常作息
```

- **闲聊模式**：不注册工具，DS 不知道数据存在。Python 关键词匹配做兜底——用户提到已有任务/项目关键词时，Python 静默把相关信息附在本轮 message 里。
- **风险**：DeepSeek function calling 质量需要早期实测（工具选择是否准确、参数格式是否正确）。如果不靠谱，备选方案是合并工具减少选择或在 prompt 里加引导。

## LLM 与 Python 的分工原则

LLM 是概率引擎，Python 是确定性引擎。两者配合，不是二选一。

- **LLM 负责**：理解用户意图、识别实体类型、评估优先级、生成草稿内容、判断用户是否确认——这些都是"不确定输入→不确定输出"的复杂问题
- **Python 负责**：文件读写（原子操作）、状态管理（状态机）、去重计数、阈值判断、弹按钮、写 task 表、关联项目——这些都是"确定输入→确定输出"的简单操作

不是让 LLM 自己直接干，而是给 LLM 配上可靠的执行器。LLM 说"用户确认了计划"，Python 负责"提取 tasks → 弹确认界面 → 写入数据库"。判断可以模糊，执行必须精确。

## v4.3 触发式信号块的处置

v4.3 是在"单 prompt 承担两个职责"前提下的优化方案。双模式架构下不再适用：
- 闲聊模式不需要信号块
- 计划模式的信号块已确定为 `confirmed: true` 判断信号（见待定项 A）

v4.3 文档保留作为历史参考，不进入生产。
