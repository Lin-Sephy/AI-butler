## 🔒 安全

### 7. BYOK api_key 加密存储（已完成）
**现状**：`user_profile.llm_api_key` **明文存 Supabase**。用户存了自己的 OpenAI key，数据库管理员（你）能看到明文。
**建议方案**：
- 选项 A：Supabase Vault（Postgres 扩展，加密存敏感字段）
- 选项 B：服务端对称加密（Render 环境变量放 encryption key，存时加密读时解密）（已选）

**工时**：2-4h（A 简单但依赖 Supabase 特性；B 代码量稍多但可控）
**优先级**：**阻塞**——用户的 key 被你看到是严重信任问题

### 8. BYOK 回退策略明确（c）
**现状**：用户没配 BYOK 时，`intent._get_client` 回退用服务端默认 DeepSeek key。**陌生人注册 → 没配 BYOK → 烧你账单**。
**三选一**：
- **A. 强制 BYOK**：没配 key 直接拒绝聊天（最安全，对用户不友好）
- **B. 共享额度限流**：默认 key 只给每个 user_id 每天 N 次（代码复杂度中）
- **C. Waitlist 关小门**：上线初期只给内测熟人开通，域名不广发（最简单）

**我倾向 C** 作为第一周策略，等真实用量看情况再切 A 或 B。
**工时**：C 是零代码（产品/推广策略）；A 是 30 分钟；B 是 2-3h

### 9. Supabase 限流配置（已完成）
**现状**：Anonymous Sign-Ins 如果被脚本大量注册，会撑爆免费额度。
**步骤**：Supabase Dashboard → Authentication → Rate Limits，确认 anonymous sign-in rate 不是无限。
**工时**：5 分钟（只是配置检查 + 可能微调）

### 10. MePage 邮箱绑定——不做就藏按钮
**现状**：当前是占位"绑邮箱功能即将开放"弹窗。用户看到按钮点了没反应 = 假功能（C 视角 A-2 原则："占位不往用户脸上贴"）。
